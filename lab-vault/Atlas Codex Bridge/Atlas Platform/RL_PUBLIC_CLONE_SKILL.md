Relational Labs Public Clone Skill

Purpose

Orient the agent to the public Relational Labs environment without requiring the PI to repeatedly point to it.

The public clone is a first-class lab surface.

It is not merely a website.

It may contain:

* published vault records
* receipts and adjudications
* doctrine and findings
* Atlas Instrument code
* frozen payloads
* scene models
* datasets
* scripts
* reproducible public baselines

Core Orientation Rule

When a Relational Labs task begins, consider the public clone part of the available working environment.

Do not require the PI to re-upload or re-explain material that can reasonably be retrieved from the published lab.

Use the public clone proactively when the task concerns:

* prior findings
* adjudications
* receipts
* vault documentation
* published doctrine
* public datasets
* existing Atlas scenes
* instrument payloads
* published scripts
* reproducibility
* comparison against a public baseline

⸻

Retrieval Order

Prefer this order when gathering Relational Labs material:

1. Public clone, for published material.
2. Connected repo or project sources, for newer or unpublished working state.
3. User-provided files or pasted material, when a specific private or current version is required.

Do not ask the PI to manually provide material that is already accessible through a higher-priority source.

⸻

Public Snapshot Rule

The public clone is a published snapshot.

Do not assume it is identical to the current private lab state.

Maintain a distinction between:

* public published state
* private or local working state
* material awaiting publication

When those states conflict, identify the conflict rather than silently blending them.

⸻

Simulation Orientation Rule

The public Atlas Instrument may serve as a model and artifact library for in-chat research.

When the PI requests a simulation, replication, extension, or new diagnostic:

1. Look for an existing public scene, model, payload, dataset, or script.
2. Retrieve the published starting material when available.
3. Bring usable assets into the chat compute environment.
4. Run the new analysis when technically feasible.
5. Compare against the published baseline where relevant.
6. Return new artifacts, figures, and interpretation.

Preferred in-chat workloads include:

* Brill-Lindquist static scenes
* source ablations
* E_ij and delta-E_ij analysis
* Frobenius norm diagnostics
* payload inspection
* source-roster modifications
* resolution tests
* scalarization comparisons
* audit plots
* derived scene analysis

Do not pretend that heavyweight numerical-relativity infrastructure is available when it is not.

⸻

Reproducibility Principle

Whenever possible, build forward from published ingredients rather than reconstructing experiments from memory.

Preferred chain:

published scene or payload → retrieved asset → local chat computation → derived result → comparison → adjudication

The public instrument should increasingly function as a reproducible starting state for new work.

⸻

Vault Awareness Rule

Treat vault material as potentially public.

Standing principle:

Vault does not mean private.
Vault means potentially publishable.

Remain alert to:

* credentials
* secrets
* PII
* private operational details
* material inappropriate for future publication

Do not assume that a vault filing is permanently private merely because it originates in the private working environment.

⸻

Behavioral Defaults

When this skill is active:

* remember the public clone without being prompted
* use it when it materially reduces reconstruction work
* distinguish published evidence from current unpublished work
* use published Atlas assets as simulation starting points when appropriate
* preserve provenance between source artifact and derived result
* avoid unnecessary requests for uploads
* identify stale or incomplete public material when discovered
