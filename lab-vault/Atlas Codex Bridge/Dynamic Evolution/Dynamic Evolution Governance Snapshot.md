# Dynamic Evolution Governance Snapshot

This note summarizes the dynamic-evolution law extracted from `ATLAS_DYNAMIC_EVOLUTION_MASTER_v2.md`.

## Purpose

The dynamic program extends Atlas from static same-time-slice GFRO/GCS extraction into a living instrument: moving sources, source-owned subjective ledgers, recurrent GFRO extraction, seams/nodes through time, and a collective relational network.

It does not yet certify an Atlas-native GR evolution method.

## Node Grammar

Node -1:
master ledger, certified source of truth, native source roster.

Node 0:
comptroller in platonic space. Registers and reconciles relations. Carries an update counter only. It is not a clock, source, force, or physical frame.

Node 1:
reserved / undefined in the dynamic handoff.

Nodes 2+:
physical sources. Each owns a subjective ledger, clock, source-centered grid, trajectory, source attributes, and jurisdiction boundary.

## Subjective Ledgers

Each source is treated as a data pocket with its own book. The source records the field from its own causal/local perspective. Node 0 links those perspectives into Node -1.

This promotes the data-pocket idea from the GCS Information Boundaries paper into dynamic architecture.

## Time

Node 2+ clocks are physical accumulators using weak-field lapse:

`alpha = 1 + Phi / c^2`

Node 0 has only an update counter. It does not imply physical interval or shared global clock.

## Sampling

Dynamic lane sampling doctrine:

- omni-radial Fibonacci rays only
- no Cartesian field sampling for dynamic extraction
- sample beyond expected GCS using headroom
- clip after zero-set discovery for storage only
- adaptive ray clipping is allowed after first extraction

## Collective Network

The collective relational network is a platonic object connecting all Node 2+ sources through time. It records jurisdiction negotiation, seams, nodes, source worldlines, and foam-cell change.

Current status:
records and diagnoses. It does not yet drive dynamics.

Research ambition:
test whether the collective network can become part of the evolution engine.

## Dynamic Evolution Loop

1. Sources move under declared dynamics.
2. GCS/GFRO jurisdiction is rederived per source.
3. Each source resamples omni-radially.
4. Subjective ledgers update.
5. Collective network updates.
6. Seams and nodes are extracted.
7. Node 0 reconciles into Node -1.

Important caveat:
the current skeleton still uses Newtonian leapfrog as the primary source-motion driver. That is a declared baseline, not final Atlas-native dynamics.

## ADM Confrontation

ADM is the comparison target, not the doctrine master.

Atlas must not inherit ADM assumptions silently. The goal is to confront ADM honestly and identify:

- agreement as validation,
- disagreement as either Atlas bug, ADM limitation, or frontier signal requiring stricter tests.
